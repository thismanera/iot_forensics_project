\subsection{Scenario 2: Operational Baseline Behaviour}
\subsubsection{Introduction and Objectives}
Scenario 1 serves as the control environment for the entirety of the experimental phase. In this scenario, the smart home network operates under standard, benign conditions without any external interference or malicious activity from the attacker node. The primary objective is to establish a mathematically verifiable "ground truth" of the network's behavior. The scenario goals in detail are the following:

\begin{enumerate}
	\item Generate realistic, benign background traffic that strictly adheres to the Manufacturer Usage Description (MUD) profiles defined previously in Table \ref{table:camera_mud} (Smart Camera) and Table \ref{table:thermostat_mud} (Smart Thermostat).
	\item Capture the raw network interactions during standard operational states such as device boot-up, time synchronization, and periodic telemetry reporting.
	\item Extract and catalogue baseline network metadata. This includes metrics such as flow durations, expected packet lengths, and Inter-Arrival Times (IAT)—to, with the objective to use them as the definitive reference point for anomaly detection in subsequent attack scenarios.
\end{enumerate}

The used code can be found in \ref{annex:scenario1_code}.

\subsubsection{Expected Behaviour and Theoretical Baselines}

To ensure statistical significance and provide a robust dataset for feature extraction, the Scenario 1 baseline simulation was executed over a continuous 60-minute capture period. Based on the programmed simulation parameters and the strict Access Control Lists defined in the MUD profiles, the theoretical network footprint of the smart home can be explicitly quantified prior to analysing the empirical Zeek data.

Because the simulated environment operates under ideal, deterministic conditions without external interference, the expected behavioural fingerprint is highly predictable:

\begin{itemize}
	\item \textbf{Smart Thermostat (Deterministic Telemetry): The device is expected to generate exactly 360 secure MQTT "keep-alive" TCP flows directed at port 8883. Additionally, the device is expected to transmit exactly 10 heavier TCP payloads representing the periodic temperature and weather measurements. 
		
		\item \textbf{Smart Camera (Volumetric Streaming):} The capture is expected to show a massive, continuous stream of outbound UDP traffic on port 50005, representing the live video feed. This will be interspersed with a low frequency of TCP port 443 connections representing the synthetic TLS cloud check-ins.
		
		\item \textbf{Network Services (Time Synchronization):} Across the 60-minute capture, the combined environment is programmed to generate exactly 6 NTP time synchronization requests.
		
		\item \textbf{Domain Name Resolution:} Over the 60-minute capture, the environment will generate exactly 120 UDP DNS queries directed to port 53 on the local gateway. The Smart Camera will generate 60 queries, one every minute, to resolve cloud API and streaming hostnames, and the Smart Thermostat will independently generate 60 queries, one every minute, to resolve its MQTT broker hostname.
		
		\item \textbf{Attacker Node:} Because this scenario establishes the benign operational baseline, the attacker node must remain completely dormant. There should be exactly zero packets originating from or directed to the attacker's IP address (\texttt{10.0.0.3}).
\end{itemize}
